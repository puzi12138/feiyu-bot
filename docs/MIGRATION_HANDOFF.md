# 换机交接 · 2026-11-18

在另一台电脑继续开发，可以直接克隆本仓库。接管正在运行的机器人还需要原机的去重、回执、故障状态以及重新登录的平台账号。两项工作可以分开进行。

## 在新电脑继续开发

先克隆源码，阅读[环境重建说明](SETUP.md)和[上游版本清单](../upstream/DEPENDENCIES.lock.json)。克隆及离线测试均可在平台账号退出的情况下进行。

```shell
git clone https://github.com/puzi12138/feiyu-bot.git
cd feiyu-bot
```

准备好插件依赖后，在仓库根目录运行 `python tests/run_heybox_offline.py` 核对评论匹配与并发写入。安装兼容的 AstrBot 宿主及视觉依赖后，运行 `python tests/run_heybox_offline.py --vision` 可一并检查识图。测试使用模拟响应与临时数据库。

本轮接续点是小黑盒识图与评论回执。原环境已完成部署，后台任务和回执核对已通过只读检查。上线后的第一条新帖因时段限制跳过，当时尚未观察到新版本对正常新帖完成识图。

| 接续项 | 当前行为 | 下一步如何确认 |
| --- | --- | --- |
| 小黑盒识图 | 每次向视觉模型查询前核对最后一条用户消息中的图片。只有带齐图片的有效结果才能建立可复用的识图缓存。 | 下个正常周期遇到带图新帖时，区分真实模型识图和命中已验证缓存。此前曾在代理的 TLS 握手阶段断开，断开方仍未查明。 |
| 小黑盒评论回执 | 根据发送时的原文、本人身份、帖子、楼层和时间窗口查找唯一平台回执，写入时再次核对原出站记录。自动核对窗口为七天。 | 查看回执核对任务是否运行。没有唯一匹配、已过窗口或并发核对时记录已变，均保留原状态。任何历史未知结果都不能重新发送。 |

代码入口为[识图适配器](../plugins/astrbot_plugin_xiaoheihe_adapter/main.py)、[评论匹配](../plugins/astrbot_plugin_xiaoheihe_adapter/xiaoheihe/unknown_receipts.py)和[后台回执核对](../plugins/feiyu_steward/heybox_reconciliation.py)。小黑盒、B站出现业务故障时，默认只做最小恢复和后台就绪验证，遵守既有时段、去重和授权。

## 如需接管在线服务

1. **先在新机准备环境。** 按清单取得上游，核验 QQ、SnowLuma、原生桥和媒体工具的版本。重建 Python 环境，检查脚本中的路径和完整性校验。原机虚拟环境带有绝对路径。四个授权范围尚待确认的上游插件仅列出处；需要其本地改动时，另行核实取得方式。
2. **确认私下交付范围。** 为延续历史状态，至少要核对小黑盒、B站、管家事故与试行、已发通知和故障转送的账本，以及相应的保护状态。这些文件可能包含个人身份、聊天或评论正文。经数据所有者确认后再约定加密传输方式，账号凭据可以在新机重新填写。
3. **安排单机切换。** 切换前核对源机在途任务，停止原机业务写入和自动拉起，再做一致快照。SQLite 开启 WAL 时只复制主数据库会遗漏最近提交。现有备份入口可能在结束后重新启动原服务，完成备份后要再次确认旧机已停止，之后再启用新机。
4. **验证状态和登录。** 在新机的业务发送功能关闭时，比对快照完整性、未知出站、已确认回执、通知和原有暂停／关闭状态。空白账本无法证明旧业务从未发送。重新登录专用 QQ、核对普通 QQ 的隔离，再按实际需要验证小黑盒、B站和模型服务的身份与权限。故障转送还需核对新机客户端路径、校验值、目标聊天和旧事件去重记录。
5. **最后恢复正常周期。** 分别确认浏览循环、识图保护和回执核对后台，再观察下一条自然到达的新内容。保持原时段、配额和业务开关；既有未知结果保留，空间同步和漫画自动发布沿用原关闭或暂停状态。

公开版提供已脱敏源码、公开素材和接续说明。原机的私有账本、账号登录资料、完整运行备份及第三方二进制均需通过各自的交接方式取得。新电脑的完整运行尚待实机验证。
